# 00 · Phase 0：第一性原理、需求辨析与 3 方案对齐

> 在写第一行代码或签 `contract.yaml` 之前运行本阶段，避免"用最高效的编排器把一个错误的问题完美解决"。

## 1. 真伪需求辨析（先怀疑问题定义）

接到任务时先自问三条：
1. **症状 vs 根因**：用户要求改 A，A 是真正病灶，还是上游 B 坏了之后暴露的症状？
   - *例*："帮我把报错藏掉 / 加个 try-except" → 症状；真实根因往往是上游契约/编码环境失效。
2. **手段 vs 目标**：用户指定了某种工具/实现（"加个缓存 / 写个多代理脚本"），这只是手段；他真正要的目标是什么（"降延迟 / 降返工 / 可溯源"）？
3. **第一性原理拆解**：剥离所有历史包袱和行业惯例后，这个问题受限于哪几个不可违背的物理/信息/系统约束？（例如：上下文窗口=有限注意力预算；语言模型=无状态纯函数；并发共享目录=状态竞争。）

## 2. 提问对齐与 3 版方案矩阵（适用设计/规划/模糊场景）

当任务存在多种技术路线或目标权重未明时，**先提 2–4 个高信息量澄清问题**，再给出 3 版方案供选择：

| 维度 | 方案 A：极简止血版 | 方案 B：平衡工程版（推荐默认） | 方案 C：彻底重构版 |
|---|---|---|---|
| **核心思路** | 最小改动解决当前痛点 | 解根因 + 加自动化防回归门禁 | 推翻旧架构重建 |
| **一阶收益** | 最快上线 | 根治当前同类问题 | 架构最干净 |
| **二/三阶影响** | 可能留技术债或掩盖相邻风险 | 适度增加测试/门禁维护成本 | 短期破坏现有兼容与迁移风险高 |
| **最强反对点（钢人反驳）** | "治标不治本，下周还会复发" | "是否对当前规模略显重？" | "ROI 过低，容易过度设计失控" |
| **回退代价** | 极低 | 低–中 | 高 |

## 3. 跨领域类比思考库

卡在局部思维时，强制把问题映射到成熟工程领域寻找成熟模式：
- **数据库 / 分布式系统**：WAL 预写日志 + Checkpoint（→ `PROGRESS.md` + `trace.jsonl`）、CAS / MVCC 隔离（→ 独立 `git worktree`）。
- **编译器与 CI/CD**：静态解析门（AST）→ 单元测试 → 集成烟雾 → 灰度回滚（→ Harness 门禁分层）。
- **版本控制**：Git 棘轮（`keep / discard`）与二分定位（`autoresearch` + `DEAD_ENDS.md`）。
- **医学 / 航空**：双盲独立评审 + 起飞前检查单（→ Generator/Reviewer 独立上下文 + Checklist）。
