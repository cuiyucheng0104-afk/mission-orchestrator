# 03 · 多环节独立审核、红队挑战与交付就绪审计

> 合并 `delivery-readiness-audit` 与深度工程审视标准：所有代码与交付产物在进入收尾前，必须经**独立上下文（物理隔离、全程只读）Reviewer** 通过四重审查，并将实测结论写入 `.kb/runs/<run-id>/review_report.md`。

## 门 1：契约与围栏核对（Contract Gate）

- 核对 `git merge-base <base> HEAD` 与 `git diff --name-status <base>..HEAD`：
  - 是否干净切自目标基线，零混入无关分支或他人未跟踪产物？
  - 改动文件是否 100% 落在 `contract.yaml` 的 `fence` 内、零触碰 `forbidden`？
- 核对 `done_when`：每一条是否都有 `trace.jsonl` 中的真实命令输出/文件证据支撑？

## 门 2：深度代码与工程质检（独立上下文 + 三维深度审查）

除了常规 Bug、边界与安全审查外，Reviewer 必须回答以下三个维度：

### A. 二阶与三阶影响推演（2nd / 3rd-Order Effects）
- 本改动直接改了 X，但它对**相邻模块、未来半年新加类似文件、用户操作习惯、系统复杂度、长期维护成本**会产生什么连锁反应？
- *例*：为了同步 Obsidian 生成 `.obsidian-sync.json`（一阶便利）→ 若未将其加入 `.gitignore`（二阶隐患）→ 可能导致个人路径随 PR 泄漏到公共仓（三阶事故）。

### B. 钢人红队反驳（Steelman Devil's Advocate）
- **先假设当前"看起来最完美的方案"是错的**：站在最强反对者视角，主动寻找推翻它的反例、极端边界与静默失效路径：
  - 换到 `Python 3.9 -I`（无环境变量隔离模式）还会过吗？
  - 换到 `LC_ALL=C` 纯 ASCII 环境（如极简 Docker / CI）会因为中文紧跟 `$VAR` 炸掉吗？
  - 缺失可选外部命令（如 `ffmpeg`、`gh`）时是体面降级/报清晰提示，还是吞错假通过？
  - 把测试要保护的脚本故意改坏一行（负向变异测试），测试集真的会红吗？

### C. 新接手工程师认知成本审计（New-Hire Cognitive Load）
- 假设明天一位完全不了解项目但能力极强的工程师来接手：
  - 有没有命名误导、职责混杂、抽象过度（为已不存在的旧问题保留的补丁）、需要读 5 份背景文档才看懂的隐含约定？
  - 核心入口是否提供了一目了然的地图与单条自检命令？

## 门 3：交付就绪实测审计（Delivery Readiness Audit）

**铁律：CI 绿 / 单测过 / 构建成功 ≠ 可交付。**
对关键能力逐一**真实运行与调用**，按四维度（详见 [audit-dimensions.md](audit-dimensions.md)）给出三态判定：
1. **功能真实性**（真接通 vs 占位/stub/静默回落）
2. **安全与权限边界**（真鉴权 vs 后门/路径穿越/信息泄露）
3. **干净目标机首启与跨环境**（`python3 -I` / `LC_ALL=C` / 无选装依赖）
4. **配置与数据前提**（密钥、外部媒体、必须预装的工具）

| 维度 / 能力 | 判定 (`ready` / `needs-config` / `blocked`) | 实测能用的 | 交付前必办阻碍 | 实测证据 (`command + exit` / `file:line`) |
|---|---|---|---|---|
| ... | ... | ... | ... | ... |

存在任何 `blocked` 时**严禁宣布可交付或提 PR**，必须带具体 `EXPECTED vs SAW` 退回上游 Loop 修复并重走独立复审。
